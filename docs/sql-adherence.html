SQL adherence

Why does Qwen’s SQL fail to run, and what fixes it? Fix in code what code can fix safely, and spend a model call only on what is left. cut keeps the reply’s SQL up to the first semicolon that ends a complete statement (sqlglot finds it, so a ; inside a string survives) and never rewrites the query. pydantic checks the SQL (one SELECT, known columns, DuckDB’s EXPLAIN) and sends its error back for one retry. json is the provider’s strict JSON-schema mode. 12 questions x 3 epochs per model and variant.

Cut + validator against validator alone, Qwen 3.8 27B

We run each eval block once. A block has several tests, but a proper statistical comparison needs several independent runs of every variant and a paired comparison on the same questions, reported with a confidence interval rather than a single percentage.

With strict JSON mode on, Qwen often ends a correct query with the end of the JSON (;"}, ;,). The cut removes it in code, so the validator sends 5 retries instead of 13, for 40% less. Every cut answer passed. When JSON mode is off, Qwen does not write that junk, so the cut finds nothing to do. Cut alone on the json run’s replies: 6 cuts, SQL errors 28% → 11%. GPT-5.4 nano and mini: 0% SQL errors with the validator, in every variant.

One failure, traced

q08 “What percentage of all trips were paid in cash?” on Qwen, pydantic. The first reply makes 2 temp tables before its SELECT. The validator answers: the SQL holds 3 statements: send exactly one SELECT, with no comments or text before or after it. The retry sends one SELECT, and DuckDB returns 14.81, the reference.

Post-processing, case by case (every change is in repairs.jsonl). The sqlglot cut: 9 answers cut, 9 of them then correct, none changed in meaning. Rewrite: 3 answers, 2 then correct. It quotes a reserved alias (JOIN zones do becomes JOIN zones AS "do"). The first post-processing, with its plain split at ;, ran 3 repaired answers to a wrong value. In q08 it dropped a stray 0, and a wrong query that would have failed returned 100 against 14.81: an error became a confident wrong number.

Not tried: GEPA prompt optimization in DSPy, set aside on purpose: it needs its own held-out training questions (a later lecture or a project option).
